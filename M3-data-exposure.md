# Milestone 3 — Critical Data Exposure on the Client Server

**Objective:** Find the critical data exposure on the client server; surface staff salaries and shareholder details.
**Authorization:** Written permission granted.

## 1. Going beyond the obvious content

Per the milestone hint, analysis moved beyond simply reading the recovered PDF reports and extended to:

- Document/file properties and metadata of the recovered PDFs and the site itself.
- The CMS fingerprint from Milestone 1 (`Mediroza CMS 1.4.2`), which indicated a "backup module" exists as part of the CMS.

This line of investigation led to the discovery of a **publicly accessible database backup file** left on the web server: `mediroza_db_backup_2019.sql`.

## 2. The exposure

The `.sql` file is a full raw export of the hospital's internal database, generated by the "Mediroza CMS 1.4.2 backup module," and was reachable without any authentication. The file header itself flags its own sensitivity:

```
-- Mediroza General Hospital - internal database backup
-- Generated by Mediroza CMS 1.4.2 backup module
-- Host: localhost    Database: mediroza_hr
-- WARNING: contains confidential staff and shareholder records
-- Backup date: 2019-08-27 02:14:03
```

This is a textbook **sensitive data exposure** / **backup file disclosure** vulnerability: an old backup was never removed from the publicly served directory, and it contains two full confidential tables.

**Evidence:** `evidence/m3-data-exposure/salaries.jfif`, `shareholders.jfif`

## 3. Task — Staff salaries

The `staff` table contains full HR records for ~30 hospital employees, including: full name, job title, department, email, phone, **national ID number**, **monthly salary (ZAR)**, and date joined.

## 5. Why this is critical

- No authentication was required to reach the backup file — it was a direct, unauthenticated file disclosure.
- The exposure combines **personal data** (PII, national IDs, salaries) with **corporate confidential data** (ownership/equity), creating both a privacy/regulatory risk (e.g. POPIA in South Africa) and a corporate/competitive risk.
- The root cause chain is the same pattern seen throughout the engagement: a weak, custom CMS (`Mediroza CMS 1.4.2`) with multiple basic security hygiene failures (SQL injection, weak default passwords, and now unremoved/publicly reachable backups).
